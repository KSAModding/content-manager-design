# Decisions

Newest first, one row per accepted RFC. This table answers "what did we decide". The RFC itself answers "why".

| Date | RFC | Decision |
|---|---|---|
| 2026-10-22 | [0104](rfcs/0104-share-host-conformance.md) | Adds spec/share-host.md, a living checklist of numbered rules that every share host follows and a steward checks at registration, with the order of writes, the upload API paths and error codes, and a test upload at registration; a change that binds a registered host needs an RFC, any other change a pull request; amends RFC 0094: hosts without GitHub storage are registered on equal footing with signed data files (Ed25519 `key` and `retired_keys` in `hosts.toml`), download rules under `downloads` and succession terms, and the snapshot embeds `hosts.toml` verbatim as `hosts`; `spec_version` and `snapshot_version` stay at `1`. |
| 2026-10-22 | [0094](rfcs/0094-share-host.md) | Adds the share host, a release host kind for vehicles and saves that a steward registers in `hosts.toml` of the authored repository and a listing names as `[releases] <host> = "<id>"`; in the recommended form its data plane is a GitHub storage repository of the operator with the release list, the owner records, the edit attestations and the archives as release assets, and its own service takes uploads, checks them by RFC 0085's rules and opens listing pull requests from its bot; ownership is proven by a file in the storage repository, and ksamods.gg is the first host; amends RFC 0031, 0033, 0052 and 0085, and moves the `vehicles` and `saves` arrays out of the main snapshot into `snapshot-vehicles.json` and `snapshot-saves.json` next to it, each with its own ETag; `spec_version` and `snapshot_version` stay at `1`. |
| 2026-10-20 | [0085](rfcs/0085-vehicles-and-saves.md) | Adds the content types `vehicle` and `save`, listed like a mod without `[loader]`, with the mods they need as authored `[[dependencies]]` that the sharing client fills from its instance; `links.forums` is optional for them; their archives go to GitHub storage of a host operator or to an external host, defined in a hosting RFC, and the index accepts these listings only once such a host exists; the watcher checks `meta.toml`, the name rule (with a vector file) and the game file, stamps `install.folder` and `game_min` from the build, and the snapshot gets optional `vehicles` and `saves` arrays; a client installs the dependencies first and never replaces or updates a player's own folder without asking; `spec_version` and `snapshot_version` stay at `1`. |
| 2026-10-16 | [0096](rfcs/0096-tag-prefix.md) | Amends `[releases]` of RFC 0031 and `since` of RFC 0079: an optional `tag_prefix` makes the watcher take only the GitHub releases whose tag starts with it and read the version from the rest of the tag; `spec_version` stays at `1`. |
| 2026-10-16 | [0095](rfcs/0095-fork-rename.md) | Amends RFC 0048: the rename redirect follows a renamed or transferred fork like any other repository, and the new name is verified with the fork rule of RFC 0079, the owner id or the topic and never the marker file; `spec_version` and `snapshot_version` stay at `1`. |
| 2026-10-16 | [0092](rfcs/0092-listed-at.md) | Amends RFC 0058: every listing and pack entry of the snapshot gets an optional derived `listed_at`, the committer time of the oldest first-parent commit on `main` of the authored repository whose tree holds a document for the id, so a rename that keeps the id and a delisting followed by a new listing keep the first time; a client may sort by it, newest first, and sorts an entry without it last; `spec_version` and `snapshot_version` stay at `1`. |
| 2026-10-16 | [0091](rfcs/0091-game-max-blocks.md) | Amends RFC 0017 and RFC 0031: content that states a `game_max` is Incompatible on a newer game, and a client blocks it as it blocks a game older than `game_min`; content without `game_max` stays Compatible on every newer game; no field is added, and `spec_version` and `snapshot_version` stay at `1`. |
| 2026-10-02 | [0081](rfcs/0081-listing-narrowing.md) | Amends RFC 0031: a merged edit of the compatibility, the loader or the dependencies of a listing reaches its newest release that is neither yanked nor `dev`, in both directions, as an amendment of the verified owner under RFC 0079 that the watcher applies on its next tick unless a release pull request of the listing is open; older releases keep their stamp, the comment on the listing pull request says which release an edit reaches, and `spec_version` and `snapshot_version` stay at `1`. |
| 2026-10-02 | [0080](rfcs/0080-pack-claims-and-members.md) | Amends RFC 0031 and RFC 0033 for packs: a first pack claim merges itself, first come, first served, and a steward no longer accepts it; every pinned mod must be a listed mod at a stamped release that is not yanked, and the pinned set must hold every required dependency of its members with no two members in conflict; a client shows how many members of a pack version have newer releases than the version pins; a mod author who asks to leave a pack gets a new pack version without the mod and a steward retracts the older versions; `spec_version` and `snapshot_version` stay at `1`. |
| 2026-09-25 | [0079](rfcs/0079-author-freedom.md) | Amends RFC 0031, 0033, 0038 and 0064: the verified owner of a listing may amend a published release in both directions, while a steward's own amendment stays narrowing only; a fork proves ownership through the owner id or the topic; a SpaceDock listing proves ownership through the GitHub repository its SpaceDock `source_code` names; `[releases] since` lets the watcher stamp older releases from that version on; the watcher follows edits of the release notes; the bytes of a release, the id rules, the ownership proof, the install descriptor, the image records and `links.forums` stay strict, and `spec_version` and `snapshot_version` stay at `1`. |
| 2026-09-25 | [0078](rfcs/0078-gone-releases.md) | The watcher marks a stamped release whose archive is gone from its host with `download.unavailable_since` in the release file, once every observation for at least 24 hours found it missing and a GET to each stamped URL answers 404, 410 or 451, and removes the field when the same bytes are served again; no mark while a mirror still serves the bytes; a client does not offer a marked release for a new install or an update, warns when a pack pin asks for it, and never touches an installed copy; the field is written only by the watcher and is outside the amendment class, and `spec_version` and `snapshot_version` stay at `1`. |
| 2026-09-25 | [0072](rfcs/0072-version-forms.md) | A release tag may name one, two or three numeric components, with an optional leading `v` and the SemVer pre-release and build parts, and the index fills a missing component with `0`, so `0.5` is stored as `0.5.0`; the stored `version` stays a full SemVer 2.0.0 version, an authored dependency or loader bound is filled by the same rule, two tags that fill to the same version are one version and the second is refused, four components stay refused, and `spec_version` and `snapshot_version` stay at `1`. |
| 2026-09-18 | [0067](rfcs/0067-per-platform-launch.md) | A `mod-loader` listing can add `[provides.platform.<os>]` for `windows`, `linux` or `macos`, each with a `launch` path and an optional `runtime`, whose only value is `dotnet`, so a manager starts that runtime with the entry file as its first argument; a manager reads only the entry of its own platform, starts `[provides].launch` when there is none, refuses to start when its own entry names something it does not know or cannot find, and `spec_version` stays at `1`. |
| 2026-09-16 | [0065](rfcs/0065-icon-center-crop.md) | A listing icon no longer has to be square: its shorter side is 256 to 1024 pixels and its longer side at most twice the shorter side, the checks give a note that names the center square instead of a reject, a client shows only that center square, every other image rule of RFC 0058 stays, and `spec_version` and `snapshot_version` stay at `1`. |
| 2026-09-16 | [0064](rfcs/0064-changelog-text.md) | A release file gets an optional `changelog_text` with the release notes as CommonMark of at most 16 KiB of UTF-8, copied by the watcher from the authority host or supplied on the release pull request of a listing without `[releases]`, where it is authoritative; a missing text can be added once and only by the watcher, a present text never changes, a client shows it offline with no images and falls back to the `changelog` link, and `spec_version` and `snapshot_version` stay at `1`. |
| 2026-09-14 | [0058](rfcs/0058-listing-images-and-dates.md) | An authored document gets an optional `[images]` table with one square icon and the images its description references as `ksa-image:<id>`, each a record with a URL on the author's host plus `sha256`, `width`, `height` and `size` that the checks and every client verify, and a client shows no other image in a description; the snapshot gets the derived optional fields `published_at` and `updated_at`, and `spec_version` and `snapshot_version` stay at `1`. |
| 2026-09-13 | [0052](rfcs/0052-static-download-counts.md) | The generated index repository carries a static `download-counts.json` with the download counts GitHub and SpaceDock report per listing and version, and the snapshot attaches them as an optional `downloads` field; an absent count means unknown, and counts never affect resolution, installation, ownership or moderation. |
| 2026-09-13 | [0049](rfcs/0049-instance-handover.md) | A `mod-loader` listing states how it is told which instance to run in a `[provides.instance]` table, a command line flag that takes the instance root as the next argument, an environment variable that carries it, or both, and a manager fills in only the absolute instance root; nothing else in RFC 0035 changes and `spec_version` stays at `1`. |
| 2026-08-15 | [0048](rfcs/0048-ownership-of-an-edit.md) | Ownership of an edit is evaluated against the authority the listing's base version names, and not against the authority the submitted document names; pointing a listing at a different release host verifies against both, a repository GitHub redirects to a new address is a rename rather than a move, and whether a listing already exists is read from the base branch and never from the file status a host reports. |
| 2026-08-10 | [0038](rfcs/0038-repository-topic-ownership-proof.md) | The ownership check accepts a third proof: the repository topic `ksa-index-<login>`, set by an administrator of the release host and naming the claiming account's login, evaluated between RFC 0033's owner-id fast path and the marker file; it closes the organization-owned repository case and changes nothing else in RFC 0033. |
| 2026-08-09 | [0035](rfcs/0035-content-install-descriptor.md) | Every content type gets an `[install]` descriptor on its authored file, an anchor plus relative path with per-type defaults and prose-only steps, and a mod loader adds `[provides]` naming its launch target, content directory, and the closed configure contract a manager machine-writes; RFC 0031's install table becomes this superset without a spec_version bump. |
| 2026-08-09 | [0033](rfcs/0033-content-index.md) | The community index lives in two GitHub repositories, authored plus generated, with a scheduled watcher stamping releases and self-service listing gated by automated ownership verification; clients fetch one snapshot artifact from a stable address with normal HTTP caching, moderation speaks through index-side states, and humans act only on disputes, takedowns, delisting, and listings whose ownership cannot be verified automatically. |
| 2026-08-08 | [0031](rfcs/0031-content-metadata-format.md) | One metadata format for every content type, a shared authored core plus per-type extensions; a mod or mod loader is one authored TOML file plus one tooling-stamped JSON file per release, a pack is one authored document per version with exact pins, ids share one global case-insensitive namespace, and a published release accepts only narrowing amendments. The vehicle and save types themselves stay a future RFC. |
| 2026-08-04 | [0025](rfcs/0025-scope.md) | The project is a content manager covering mods, mod packs, vehicles, and saves, with the content type a required metadata field from day one; the index is our own on free infrastructure, StarMap stays an external dependency, Borea is the implementation, and the repository is renamed to match. |
| 2026-08-03 | [0017](rfcs/0017-game-version-ordering-and-compatibility.md) | KSA releases are ordered by their revision alone; a mod's compatibility is a revision range with a required lower bound and an optional open upper bound. |
